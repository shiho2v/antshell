## 1. 개요 (Overview)

본 SPEC은 대시보드의 하드코딩된 뉴스 영역을, **선택한 종목에 연동된 실제 수집 뉴스**로 교체한다. 백엔드는 이미 커밋된 파일만 읽어 서빙하고, 프론트엔드는 대시보드 안의 뉴스 영역 한 곳만 바꾼다. 새 화면이나 새 라우트 경로 계층은 만들지 않는다.

### 1.0 선행 SPEC과의 관계

- **`SPEC-API-001`** (8주차, 백엔드 API ↔ 대시보드 실데이터 연동)은 현재 `status: draft`이며 구현되지 않았다. `backend/app/main.py`에 `/api/stocks` 목록 라우트가 없고, `frontend/src/app/dashboard/page.tsx:18`은 여전히 `MOCK_STOCKS` 하드코딩 배열을 쓴다. 본 SPEC은 `depends_on`을 선언하지 않는다. 신규 라우트 `GET /api/stocks/{code}/news`는 `SPEC-API-001`이 만들 `/api/stocks` 목록 라우트와 경로가 겹치지 않으며, `MOCK_STOCKS` 제거는 `SPEC-API-001`의 몫이다(§5).
- **`SPEC-CHART-001`** (9주차, `status: in-progress`)이 확립한 두 가지 구현 패턴을 그대로 계승한다. 첫째, **요청 경로에서 데이터 수집을 트리거하지 않는다**. 둘째, **허용 목록 검사를 파일 시스템 접근보다 먼저 수행한다**(`backend/app/main.py`의 `_load_ohlcv_or_404`). 종목 허용 목록도 `SPEC-CHART-001`과 같은 4개를 쓴다(§1.3). 본 SPEC은 `SPEC-CHART-001`의 자산(`data/{code}_ohlcv.json`, `StockChart.tsx`, 차트 라우트 2개)을 읽지도 고치지도 않는다.
- **`SPEC-PORTFOLIO-001`** (10주차, `status: draft`)과는 **의존 관계가 없다.** 다만 `backend/app/main.py`·`frontend/src/app/dashboard/page.tsx`·`docs/weekly/WEEK_10.md` 세 파일을 양쪽이 함께 건드린다. 서로 다른 구간만 수정하도록 나누는 방법은 `plan.md` §A.4에 있다.

아래는 2026-09-20에 저장소 파일을 직접 읽어 확인한 사실이다. 스크립트를 실행해 얻은 값은 없다.

여기서 세 가지 공백이 나온다.

1. **`008490` 뉴스 파일이 없다.** 허용 목록에 있는 종목인데 서빙할 원본이 없다. 사람이 스크립트를 1회 실행해 만들어야 한다(REQ-001).
2. **선언 스키마와 실제 파일이 어긋난다.** `url`은 에이전트 선언에 없지만 실제 파일에는 있다. 따라서 `url`을 **선택 필드**로 취급해야 하고, 있을 때와 없을 때의 화면 동작을 둘 다 정해야 한다(§4 「안전한 링크」, REQ-009).
3. **`date` 값의 형태가 일정하지 않다.** 현재 허용 목록 4개 종목의 커밋된 파일에는 ISO 날짜만 있지만, 파싱 불가 값이 실제로 발생한 전례가 `005380_agents.json`에 남아 있다. `008490`을 새로 수집하면 같은 형태가 나올 수 있다. 값을 고쳐 쓰지 않고 정렬로만 해소한다(§4 「뉴스 정렬 규칙」).

### 1.2 설계 결정

| 계층 | 책임 |
|------|------|
| 생성 (오프라인) | 사람이 `scripts/orchestrate_stock_agents.py`를 직접 실행해 `data/{code}_agents.json`을 만들고 커밋한다. 본 SPEC에서 실제로 실행이 필요한 것은 `008490` 한 건이다(REQ-001) |
| 서빙 | 백엔드는 커밋된 파일만 읽어 `news` 배열을 응답한다. `claude` 실행·`subprocess` 생성·외부 네트워크 호출·`data/` 쓰기를 하지 않는다(REQ-007) |
| 표시 | 대시보드의 뉴스 영역이 선택된 종목의 뉴스를 표시한다. 새 페이지를 만들지 않고 기존 영역을 교체한다 |

세 가지 결정을 여기서 못 박는다. 되돌리기 비용이 큰 순서다.

**결정 1 — 기존 파일 재사용, 새 형식 없음.** `data/{code}_news.json` 같은 새 파일을 만들지 않는다. `news` 배열은 이미 원하는 형태로 커밋되어 있고, 새 형식을 도입하면 수집 스크립트도 함께 바꿔야 하며 두 파일의 동기화 문제가 새로 생긴다. 대신 같은 파일 안의 `financials`는 **응답에 절대 싣지 않는다**(REQ-003) — 그 객체의 스키마는 `financial-data` 에이전트가 독립적으로 정하므로, 뉴스 계약이 거기에 묶이면 재무 스키마가 바뀔 때 뉴스 API가 함께 깨진다.

**결정 2 — 날짜 문자열은 절대 고쳐 쓰지 않는다.** `"2026-07 (중순)"`을 `"2026-07-15"` 같은 값으로 정규화하면 원래 없던 정밀도를 만들어 낸다. 저장된 문자열을 그대로 표시하고, 순서만 §4 「뉴스 정렬 규칙」으로 정한다.

**결정 3 — 수집 스크립트는 고치지 않는다.** `scripts/orchestrate_stock_agents.py`에 허용 목록 검사가 없는 것은 사실이지만, 본 SPEC이 요구하는 실행은 운영자가 코드를 직접 입력하는 1회 수동 단계다(REQ-001). 스크립트에 검사를 넣으면 스크립트 측 요구사항·인수 기준·테스트가 따라붙어 Tier M 범위를 넘는다. 허용 목록 밖 파일이 실수로 생기더라도 **무엇을 서빙할지는 백엔드 허용 목록이 결정하므로**(REQ-005) 노출 위험은 없다. 실제로 `data/005380_agents.json`이 이미 존재하지만 이 코드는 절대 서빙되지 않는다.

### 1.3 종목 범위

`SPEC-CHART-001`과 동일한 4개 종목으로 한정한다 — `005930` 삼성전자, `000660` SK하이닉스, `009150` 삼성전기, `008490` 서흥. 사용자가 다른 코드를 요청하는 경로는 없으며, 요청하더라도 허용 목록 검사에서 거부된다(REQ-005). 종목 범위 확장은 본 SPEC의 대상이 아니다(§5).

## 2. 요구사항 (GEARS)

### 데이터 원본

**REQ-001** [Ubiquitous] 운영자는 `python scripts/orchestrate_stock_agents.py 008490 --save`를 1회 실행해 `data/008490_agents.json`을 만들고, 그 내용이 §4 「유효한 뉴스 문서」를 만족함을 확인한 뒤 저장소에 커밋한다. 이 실행은 자동화하지 않는 사람의 수동 단계이며, `scripts/` 아래 코드는 본 SPEC에서 수정하지 않는다.

### 백엔드 — 뉴스 서빙

**REQ-002** [Event-driven] **When** 클라이언트가 `GET /api/stocks/{code}/news`를 요청하고 `code`가 §1.3 허용 목록에 있으며 `data/{code}_agents.json`이 존재하고 §4 「유효한 뉴스 문서」를 만족하면, 백엔드는 `200`과 함께 §4 「응답 계약」이 정한 본문을 반환한다 — `news` 배열의 순서는 §4 「뉴스 정렬 규칙」을 따르고, 각 항목의 `date`는 파일에 저장된 문자열 그대로이며, `url`은 파일에 있을 때만 포함된다.

**REQ-003** [Unwanted] 백엔드는 `news` 배열 밖의 파일 내용을 응답에 포함하지 않는다 — `financials`·`ticker`·`name`은 파일에 있더라도 응답 본문 어디에도 나타나지 않는다.

**REQ-004** [Event-driven] **When** `code`가 허용 목록에 있으나 `data/{code}_agents.json`이 존재하지 않으면, 백엔드는 `404`를 반환한다.

**REQ-005** [Event-driven] **When** `code`가 §1.3 허용 목록에 없으면, 백엔드는 파일 시스템에 접근하기 전에 `404`를 반환한다.

**REQ-006** [Event-driven] **When** `data/{code}_agents.json`이 JSON으로 파싱되지 않거나 §4 「유효한 뉴스 문서」를 만족하지 못하면, 백엔드는 `500`과 함께 일반화된 메시지만 반환하며, 응답 본문에 파일 시스템 경로·파일명·예외 클래스명·`Traceback` 문자열을 포함하지 않는다.

**REQ-007** [Unwanted] 백엔드는 `GET /api/stocks/{code}/news` 호출로 `claude` 실행·`subprocess` 생성·외부 네트워크 호출을 하지 않으며, `data/` 아래에 어떤 파일도 만들거나 고치지 않는다.

### 프론트엔드 — 대시보드 뉴스 영역

**REQ-008** [Event-driven] **When** 사용자가 대시보드 보유 종목 테이블에서 종목을 선택하면, 뉴스 영역은 그 종목의 뉴스를 응답에 실린 순서 그대로 표시하며, 항목마다 `title`·`source`·`date`·`summary` 네 값을 모두 **일반 텍스트로**(문자열 안의 마크업을 원시 HTML로 해석하지 않고) 표시하고 `date`는 응답 문자열을 그대로 보여 준다.

**REQ-009** [Where] **Where** 뉴스 항목이 §4 「안전한 링크」를 만족하는 `url`을 가지면, 프론트엔드는 제목을 새 탭에서 열리는 링크(`target="_blank"`, `rel="noopener noreferrer"`)로 렌더링하고, 그렇지 않으면 제목을 링크 없는 텍스트로 렌더링한다.

**REQ-010** [State-driven] **While** 뉴스 목록을 표시할 수 없는 상태가 이어지는 동안 — 선택된 종목 없음, 요청 진행 중, 요청 실패(네트워크 오류·`404`·`500`), 응답의 `news`가 빈 배열 — 프론트엔드는 네 상태를 서로 구분되는 안내로 뉴스 영역 안에서만 표시하고, 대시보드의 나머지 영역 렌더링을 중단하지 않는다.

**REQ-011** [Event-driven] **When** 직전 요청이 끝나기 전에 사용자가 다른 종목을 선택하면, 뉴스 영역은 현재 선택된 종목이 아닌 종목의 응답을 표시하지 않는다.

**REQ-012** [Ubiquitous] 뉴스 영역은 표시 중인 내용이 실시간 뉴스가 아니라 사전 수집된 스냅샷임을 알리는 문구를 함께 표시한다. 수집 시각이나 수집 방법을 나타내는 필드는 원본 파일에 존재하지 않으므로(§1.1), 그러한 값을 만들어 표시하지 않는다.

**REQ-013** [Unwanted] 프론트엔드는 하드코딩된 뉴스 목록을 표시하지 않으며, `frontend/src/app/dashboard/page.tsx`에 `MOCK_NEWS` 상수와 그 렌더 구간이 남지 않는다.

**REQ-014** [Where] **Where** 환경 변수 `NEXT_PUBLIC_API_URL`이 설정되어 있으면 프론트엔드는 그 값을 API 주소로 사용하고, 설정되어 있지 않으면 `http://localhost:8000`을 사용한다.

### 기존 기능 호환성

**REQ-015** [Ubiquitous] 기존 라우트(`GET /health`, `GET·PUT·DELETE /api/settings/notion`, `POST /api/report/notion`, `GET /api/github/issues`, `GET /api/stocks/{code}/ohlcv`, `GET /api/stocks/{code}/indicators`), 대시보드의 뉴스 영역 이외 구간(포트폴리오 요약, 보유 종목 테이블, 주가 차트, GitHub 이슈, Notion 저장 버튼, 헤더), 그리고 `data/` 아래 기존 파일의 `news` 배열 밖 내용은 변경되지 않는다.

## 4. 데이터 계약 (구현 아님)

### `data/{code}_agents.json` — 본 SPEC이 읽는 부분

```
{
  "ticker": str,              // 읽지만 응답에 싣지 않는다
  "name": str,                // 선택. 005930 파일에는 없다. 응답에 싣지 않는다
  "news": [
    {
      "title":   str,         // 필수
      "date":    str,         // 필수. ISO 날짜일 수도, 아닐 수도 있다
      "source":  str,         // 필수. 언론사 이름
      "summary": str,         // 필수
      "url":     str          // 선택. news-collector 선언 스키마에는 없으나 000660 파일에는 있다
    }
  ],
  "financials": { ... }       // 본 SPEC은 읽지도 싣지도 않는다 (REQ-003)
}
```

`news` 항목의 `source`는 **언론사 이름**이지, `SPEC-CHART-001`의 `source`(`pykrx` | `sample` — 데이터 출처 구분)와 같은 뜻이 아니다. 이름이 같을 뿐 다른 값이다.

### 「유효한 뉴스 문서」 (REQ-001 · REQ-002 · REQ-006 공통 술어)

파일이 "스키마를 만족한다"는 말의 뜻을 여기 한 곳에서만 정의한다. 운영자의 생성 후 확인(REQ-001)과 백엔드의 읽기 시 검사(REQ-002·REQ-006)는 이 정의를 그대로 쓴다. 두 곳이 서로 다른 집합을 쓰면 "커밋은 통과했는데 서빙이 500"이라는 비대칭이 남는다.

아래 네 조건을 모두 만족할 때에만 「유효한 뉴스 문서」다.

1. 파일 내용이 **JSON 객체**로 파싱된다.
2. 최상위에 `news` 키가 있고 그 값이 **리스트**다.
3. `news`의 모든 원소가 **객체**다.
4. `news`의 모든 원소가 `title`·`date`·`source`·`summary` **네 키를 모두 가지며**, 각 값이 **문자열**이다.

위반이 아닌 것을 함께 못 박는다. 이 경계가 없으면 구현자마다 다르게 읽는다.

- **열거되지 않은 키의 존재나 부재는 위반이 아니다** — `ticker`·`name`·`financials`의 유무, 원소의 `url` 유무 모두 정상이다.
- **`news`가 빈 리스트인 것은 위반이 아니다.** 뉴스 0건은 정상 경로이며 화면이 별도 상태로 안내한다(REQ-010).
- **값의 내용은 판정 대상이 아니다.** `date`가 ISO 날짜가 아니어도, 문자열이 비어 있어도 위반이 아니다. 날짜 형태는 아래 정렬 규칙이 다루는 정상 경로다.
- **`url`의 값은 판정 대상이 아니다.** 안전하지 않은 스킴이어도 문서는 유효하며, 화면이 링크를 만들지 않을 뿐이다(REQ-009).

### 「뉴스 정렬 규칙」 (REQ-002 · REQ-008 공통 정의)

먼저 「파싱 가능한 날짜」를 정의한다. `date` 값이 문자열이고, 정규식 `^\d{4}-\d{2}-\d{2}$`에 **전체가 일치**하며, 그 값이 **달력상 실제로 존재하는 날짜**일 때에만 파싱 가능하다. 형식은 맞지만 존재하지 않는 날짜(`2026-02-30`)는 파싱 불가다. `"2026-07 (중순)"`처럼 여분의 문자가 붙은 값도 파싱 불가다.

정렬은 다음 순서로 정한다.

1. 파싱 가능한 항목이 **앞**, 파싱 불가한 항목이 **뒤**에 온다.
2. 파싱 가능한 항목끼리는 **날짜 내림차순**(최신이 위)으로 정렬한다.
3. 날짜가 같은 항목끼리는 **파일에 저장된 상대 순서를 유지한다**(안정 정렬). `005930_agents.json`에 같은 날짜가 2건씩 있으므로 이 규칙은 실제 데이터에서 동작한다.
4. 파싱 불가한 항목끼리는 **파일에 저장된 상대 순서를 그대로 유지한다.** 이들 사이에는 어떤 순서 판단도 하지 않는다.
5. 어느 경우에도 `date` 문자열은 **원문 그대로** 응답에 실린다. 정규화·재작성·보정을 하지 않는다(§1.2 결정 2).

### 「안전한 링크」 (REQ-009 정의)

뉴스 항목의 `url`이 아래를 **모두** 만족할 때에만 안전한 링크다.

- `url` 키가 존재한다.
- 값이 문자열이다.
- 대소문자를 구분하지 않고 `http://` 또는 `https://`로 시작한다.

키 부재, 문자열이 아닌 값, 빈 문자열, 그 밖의 스킴(`javascript:`·`data:`·`file:` 등), 스킴 없는 상대 경로는 모두 안전하지 않은 것으로 본다.

이 판정을 **프론트엔드가** 수행하는 이유를 적어 둔다. 백엔드 응답은 저장된 `news` 배열을 그대로 내보내는 것으로 정의했고(아래 「응답 계약」), 값을 들여다보고 필드를 떼어 내기 시작하면 날짜 문자열을 원문 그대로 싣는다는 결정(§1.2 결정 2)과 어긋난다. 또한 백엔드가 조용히 `url`을 지우면 화면은 "링크가 없는 기사"와 "안전하지 않은 링크를 가진 기사"를 구분할 수 없다. 앵커 요소를 만드는 쪽이 만들지 말지를 판단한다.

### `GET /api/stocks/{code}/news` 응답 계약

```
{
  "stock_code": str,          // 요청한 코드를 그대로 되돌려준다
  "news": [                   // 「뉴스 정렬 규칙」 순서
    { "title": str, "date": str, "source": str, "summary": str, "url": str? }
  ]
}
```

- 최상위 키는 **정확히 이 두 개**다. `financials`·`ticker`·`name`은 포함하지 않는다(REQ-003).
- `news` **항목**의 키는 위 다섯 개로 한정하지 않는다. 파일의 항목에 위에 열거되지 않은 키가 있으면 **그대로 응답에 싣는다** — 항목에서 키를 골라 뽑지 않는다. 최상위(고정 2키)와 항목(통과)의 처리가 다른 이유는, 최상위는 `financials` 노출을 막아야 하는 반면(REQ-003) 항목은 저장된 내용을 그대로 내보내는 계약이기 때문이다(아래 「안전한 링크」의 판정 주체 근거와 같은 이유). 화면은 위 다섯 키만 읽으므로 통과된 키는 표시에 영향을 주지 않는다.
- 건수를 나타내는 별도 필드를 두지 않는다. `news` 배열의 길이가 곧 건수이고, 파생 필드를 하나 더 두면 배열과 어긋날 여지만 생긴다.
- `url`은 파일의 해당 항목에 있을 때만 실린다. 없는 항목에 빈 문자열이나 `null`을 채워 넣지 않는다.
- 응답에 수집 시각·수집 방법 필드를 넣지 않는다. 원본 파일에 그런 값이 없기 때문이다(§1.1).

### 기존 파일과의 관계

- `data/{code}_agents.json`: 본 SPEC이 읽는 유일한 데이터 파일. `008490`만 새로 생성한다(REQ-001).
- `data/005380_agents.json`: 허용 목록 밖 코드의 파일. **존재하지만 절대 서빙되지 않는다**(REQ-005).
- `data/{code}_ohlcv.json`·`{code}_market.json`·`{code}_fundamentals.json`: 다른 SPEC의 자산. 읽지도 쓰지도 않는다.
- `data/portfolio*.json`: `SPEC-PORTFOLIO-001`의 입력. 본 SPEC과 무관하다.

## 5. 제외 범위 (Out of Scope)

### Out of Scope — 사용자별 관심 종목과 개인화
- 로그인 사용자별 보유 종목·관심 종목 등록 화면, Supabase 관심 종목 테이블, 사용자별로 다른 뉴스 목록. 본 SPEC의 뉴스는 대시보드에서 선택한 종목 하나에만 연동되며 사용자와 무관하다. 관심 종목 저장은 후속 `SPEC-WATCHLIST-001`(미작성)의 범위로 남겨 둔다 — 본 SPEC은 그 설계를 하지 않는다.

### Out of Scope — 4개 종목 밖 확장
- `005930`·`000660`·`009150`·`008490` 이외 종목의 뉴스 수집·서빙·표시. 사용자가 임의 코드를 요청하는 입력 경로를 만들지 않으며, 허용 목록 밖 코드는 `404`로 거부한다(REQ-005). 이미 존재하는 `data/005380_agents.json`도 서빙 대상이 아니다.

### Out of Scope — 실시간 갱신과 자동 재수집
- 실시간 뉴스 스트리밍, WebSocket 갱신, 폴링 기반 자동 새로고침, cron·GitHub Actions·백그라운드 잡을 통한 자동 재수집, 데이터 만료 감지 후 자동 갱신. 재수집은 사람이 스크립트를 직접 실행하는 수동 절차다.

### Out of Scope — 뉴스 검색·필터·페이지네이션
- 키워드 검색, 기간 필터, 언론사 필터, 더 보기·무한 스크롤·페이지 번호. 화면은 파일에 있는 뉴스를 정렬된 순서로 한 번에 모두 표시한다.

### Out of Scope — 요청 경로의 LLM 호출과 요약·감성 분석
- 요청 처리 중 `claude` 실행, 서브에이전트 호출, 임의 LLM API 호출(REQ-007). 기사 감성 점수 산출, 요약 재작성, 키워드 추출, 종목별 뉴스 점수화. `summary`는 수집 시점에 `news-collector`가 만든 문장을 그대로 표시할 뿐이며 본 SPEC은 어떤 해석도 덧붙이지 않는다.

### Out of Scope — `financials` 데이터 노출
- `data/{code}_agents.json`의 `financials` 객체를 API로 서빙하거나 화면에 표시하는 일(REQ-003). 재무 데이터 화면은 별도 과제다.

### Out of Scope — 대시보드의 다른 MOCK 데이터 교체
- `MOCK_STOCKS` 제거와 보유 종목 테이블 실데이터 연동, 포트폴리오 요약 숫자의 실데이터 교체. `MOCK_STOCKS`는 `SPEC-API-001`의 범위이며 본 SPEC이 대신 구현하지 않는다. 본 SPEC이 제거하는 하드코딩 데이터는 `MOCK_NEWS` 하나다(REQ-013).

### Out of Scope — 수집 스크립트 변경
- `scripts/orchestrate_stock_agents.py`에 허용 목록 검사·저장 전 스키마 검사·원자적 저장을 추가하는 일. 근거는 §1.2 결정 3이다. `scripts/` 아래 어떤 파일도 수정하지 않으므로 `scripts/tests/`도 건드리지 않는다.

### Out of Scope — 프론트엔드 테스트 프레임워크 도입
- jest·vitest·`@testing-library` 등 컴포넌트 테스트 인프라 신설과 그에 따른 `frontend/package.json` 의존성 추가. 현재 저장소에 프론트엔드 테스트 프레임워크가 없으며, 화면 요구사항(REQ-008~REQ-014)은 `docs/weekly/WEEK_10.md`에 기록하는 **문서화된 수동 검증 절차**와 기존 자동 게이트(`npm run lint`, `npm run build`)로 판정한다. 대응 관계는 `acceptance.md` 「검증 수단」 표에 있다.

### Out of Scope — 신규 엔드포인트 인증
- `GET /api/stocks/{code}/news`에 인증·인가를 적용하는 일. 기존 읽기 라우트(`/api/github/issues`, `/api/stocks/{code}/ohlcv`, `/api/stocks/{code}/indicators`)와 동일하게 무인증으로 유지한다. 이 비대칭은 의도적이다 — 대시보드 접근에는 Supabase 로그인이 필요하지만 이 엔드포인트 자체는 열려 있다. 서빙 대상이 저장소에 커밋된 공개 기사 메타데이터이고 개인정보를 담지 않기 때문이며, `§5 사용자별 관심 종목`이 후속 SPEC에서 들어와 응답이 사용자별로 달라지는 순간 이 엔드포인트의 인증 적용이 선행 조건이 된다.
